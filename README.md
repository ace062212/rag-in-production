# RAG in Production — 운영에서 배운 것들

공공 대국민 AI 챗봇의 RAG 파이프라인을 5개월간 만들고 고치면서 남긴 기록입니다.
튜토리얼이 아니라 **실제로 틀렸던 것과, 왜 틀렸는지**를 적었습니다.

> 회사 코드·데이터·인프라 정보는 포함되어 있지 않습니다. 구조와 판단만 다룹니다.

---

## 0. 파이프라인 구조

```
질문 + 대화맥락
  ① 라우팅        Rule → 규칙 교차검증(margin) → 검색기반 top-1 → LLM 폴백
  ② 질문 정규화    sLLM — 오타 교정 + 생략 문맥 복원
  ③ 하이브리드 검색  Elasticsearch(nori) — KNN + BM25, RRF k=60
  ④ 리랭킹        BGE-Reranker-M3 → 상위 N건
  ⑤ 프롬프트 조립   도메인별 시스템 프롬프트
  ⑥ 생성          LLM 32B, SSE 스트리밍
```

도메인이 여러 개(교통·행정·연금·통관…)라 **어느 인덱스를 볼지 정하는 게 첫 번째 문제**였고,
그게 정해진 뒤에도 **검색 성공 ≠ 정답**이라는 두 번째 문제가 남았습니다. 아래는 그 두 개 이야기입니다.

---

## 1. "환각"이라고 부르기 전에 컨텍스트와 대조하라

운영 평가(수십 문항 규모) 결과:

| 지표 | 결과 |
|---|---|
| 정답 문서 검색 성공 | **90%대** |
| 최종 답변 정합성 | **40%대** |

격차가 40%p를 넘었습니다. 검색이 아니라 생성 문제라는 건 명확했는데, **원인을 특정할 수 없었습니다.**

그래서 오답으로 지적된 문구를 전부 실제 LLM 입력 컨텍스트와 한 줄씩 대조했습니다.

```
컨텍스트에 있었음 (문서 혼합)  ~3/4
컨텍스트에 없었음 (창작)       ~1/4
```

**"모델이 지어냈다"고 보고했던 것의 대부분이 사실은 문서 혼합이었습니다.**
상위 후보에 무관 문서가 섞이고 모델이 그걸 하나로 합성한 것이지, 없는 말을 만든 게 아니었습니다.

이게 중요한 이유: 두 경우의 **고칠 레이어가 다릅니다.**

| 실제 원인 | 고칠 곳 | 프롬프트로 고쳐지나 |
|---|---|---|
| 무관 문서 혼합 | 검색 · 리랭킹 임계값 | ❌ |
| 절차 재구성 중 UI 단계 창작 | 프롬프트 | ✅ |
| 지식 데이터 버전 충돌 | **데이터 정리** | ❌ 절대 |
| 리랭커가 정답을 컷 | 임계값 · 인덱싱 | ❌ |

> **한 번 잘못 셌습니다.** 컨텍스트 대조 없이 지적 건수를 전부 "창작"으로 집계했다가,
> 대조 후 실제 창작은 4분의 1뿐이었습니다. 잘못 센 수치는 잘못된 곳을 고치게 만듭니다.
> RAG 결함 집계에서 컨텍스트 대조는 선택이 아니라 전제조건입니다.

### 프롬프트로 못 고치는 것의 대표 사례

한 인덱스 안에 이런 두 문장이 공존하고 있었습니다.

```
"○○년 기준 금액: A"
"○○년 기준 금액: B (익년 적용)"
```

같은 항목의 구·신 금액이 한 인덱스 안에 남아 있었고, 모델은 구버전을 골랐습니다.
**모델 잘못이 아닙니다.** 지식베이스가 두 개의 진실을 동시에 갖고 있으면
어떤 프롬프트를 써도 확률적으로 반은 틀립니다. 데이터를 고쳐야 합니다.

## 2. 리랭커는 정답을 통째로 버릴 수 있다

한 질문에서 KNN top-1이 **정답 청크**였는데, 리랭커가 임계값을 크게 밑도는 점수를 주고 후보 전건을 컷했습니다.
결과는 "정보 없음". 검색 지표상으로는 **성공**으로 잡히는 케이스입니다.

원인은 어휘 격차였습니다. 질문의 핵심 단어가 해당 인덱스 전체에 **0건**이었습니다.
BM25는 애초에 못 잡고, 벡터는 잡았는데, 리랭커가 표면 어휘 불일치로 낮은 점수를 줬습니다.

**얻은 규칙**
- 리랭커 threshold는 상수가 아니라 **인덱스별 어휘 분포의 함수**다
- "top-k 안에 정답이 있었나"와 "그게 살아남았나"는 **분리해서 측정**해야 한다
- 전부 컷되면 "정보 없음"이 아니라 **컷 사실 자체를 로깅**해야 원인이 보인다

### Logit을 신뢰도로 보여줄 때

리랭커 출력은 logit이라 음수가 흔합니다(예: -5.3).
이걸 그대로 시그모이드에 넣으면 관련 있는 문서가 사용자에게 **신뢰도 0.5%** 로 표시됩니다.

점수 체계의 원점이 0이 아닌 것뿐인데 UI가 거짓말을 하게 됩니다.
오프셋 보정으로 해결했지만, 교훈은 **모델 내부 점수를 사용자 지표로 그대로 노출하지 말 것**입니다.

## 3. 라우팅 — 전처리가 의도를 지운다

사용자가 `srt`를 `str`로 오타냈습니다.
전처리 sLLM이 오타 교정 과정에서 `str`을 **삭제**했고, 도메인 단서가 사라져 일반 대화로 분류됐습니다.

문제는 순서였습니다. **라우팅이 전처리된 질문을 보고 있었습니다.**

```diff
- route(normalize(query))     # 정규화가 의도 단서를 지울 수 있음
+ route(query)                # 라우팅은 원본을, 검색은 정규화본을
```

**LLM 전처리는 정보를 추가하는 게 아니라 재작성합니다. 재작성은 손실 연산입니다.**
의도 판정처럼 손실에 민감한 단계는 원본을 봐야 합니다.

라우팅은 최종적으로 4단 폴백 + 게이트 구조가 됐습니다.

```
Rule 매칭
  → 규칙 교차검증 (margin 이하면 불확실 처리)
  → 검색 기반 (도메인별 top-1 점수 비교)
  → LLM 폴백
+ 마진 게이트 · 세션 고착 · 비활성 도메인 차단
```

세션 고착이 필요했던 이유: 대화 중 후속 질문("그럼 환불은요?")은 도메인 단서가 없습니다.
매 턴 독립 라우팅하면 두 번째 질문에서 도메인이 튑니다.

---

## 4. 답변 편차 — 조사 하나로 답이 바뀌던 문제

거의 같은 질문인데 답이 달랐습니다. 두 가지가 겹쳐 있었습니다.

1. 조사 차이 → 검색 순서 변화 → 다른 컨텍스트
2. `temperature 0.7` → 같은 컨텍스트에서도 다른 답

**정보 제공형 RAG에 0.7은 너무 높습니다.** 0.1로 낮춘 뒤 편차가 크게 줄었습니다.
챗봇의 "자연스러움"은 temperature가 아니라 프롬프트와 페르소나에서 나옵니다.

### 그리고 LLM에게 판단을 맡기지 말아야 할 것

참고 지식에 이미지가 있어도 모델이 "관련 없다"고 스스로 판단해 생략하는 일이 잦았습니다.
지침을 이렇게 바꿨습니다.

> 관련성을 판단하지 말고, 지식 내 이미지·링크는 기계적으로 그대로 출력할 것.

**결정론적으로 처리 가능한 것에 모델의 재량을 주지 마세요.** 재량은 곧 편차입니다.

## 5. 요약 — 다음에 처음부터 할 것들

- [ ] 결함은 **반드시 실제 컨텍스트와 대조 후** 집계한다 (혼합 vs 창작 분리)
- [ ] 검색 성공률과 답변 정합성을 **따로** 본다. 격차가 개선 방향을 알려준다
- [ ] "top-k에 있었나" / "리랭커를 통과했나"를 분리 측정하고, 전건 컷을 로깅한다
- [ ] 라우팅은 원본 질문으로, 검색은 정규화 질문으로
- [ ] 리랭커 threshold는 인덱스별로 재검증한다
- [ ] 모델 내부 점수를 사용자 신뢰도로 직접 노출하지 않는다
- [ ] 정보 제공형은 temperature를 낮춘다
- [ ] **지식베이스 버전 충돌은 프롬프트로 못 고친다.** 데이터 정합성이 먼저다
- [ ] 프롬프트 수정 후엔 회귀 케이스 세트로 재검증한다 (고치면 다른 게 깨진다)
